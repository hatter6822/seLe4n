## Політика гілок

- **Ніколи не робіть push безпосередньо в `main`.** Створіть гілку функції,
  запуште її та дайте супроводжувачу об'єднати зміни через PR.
- Один зв'язний зріз (coherent slice) на гілку. Якщо зріз виростає більшим,
  ніж очікувалося, розділіть його перед запитом на рев'ю.
- Ідентифікатори робочих потоків вказуються в повідомленнях комітів та описі
  PR, а не в іменах ідентифікаторів коду (див. «Internal-first naming» у
  [`CLAUDE.md`](../../../CLAUDE.md)).

## Pre-commit хук (обов'язково)

Перед першим комітом встановіть pre-commit хук:

```bash
./scripts/install_git_hooks.sh
```

Хук збирає кожен змінений модуль `.lean` через `lake build <Module>` і
відхиляє будь-який коміт, що вносить `sorry`. **Не обходьте його за
допомогою `--no-verify`** — якщо він блокує коміт, виправте першопричину.

`scripts/setup_lean_env.sh` автоматично запускає інсталятор; CI викликає
`./scripts/install_git_hooks.sh --check`, щоб забезпечити наявність хука в
клоні контриб'ютора для будь-якого об'єднаного PR.

## Обов'язкова валідація перед відкриттям PR

```bash
./scripts/test_smoke.sh     # мінімальний поріг (Рівні 0-2)
./scripts/test_full.sh      # обов'язково для змін теорем/інваріантів (Рівні 0-3)
```

Для змін на боці Rust додатково запустіть:

```bash
cd rust && cargo test --workspace && cargo clippy --workspace -- -D warnings
```

Для змін ABI / рівня декодування також запустіть:

```bash
./scripts/test_abi_roundtrip.sh
./scripts/test_rust_conformance.sh
```

## Умова розміру файлів (стеля 2000 LOC)

Продуктові модулі `.lean` ПОВИННІ залишатися під **2000 LOC**. Файли, що
переросли цю стелю, розбиваються на хаб реекспорту та дочірні модулі
(приклади: `SeLe4n/Kernel/IPC/Invariant/Structural.lean`,
`SeLe4n/Kernel/Capability/Invariant/Preservation.lean` та
`SeLe4n/Kernel/Lifecycle/Operations.lean`). Файли-хаби є тонкими агрегатами
лише для реекспорту (import-only), щоб наявні інструкції `import`
продовжували працювати без змін після розбиття.

Якщо ваша зміна виштовхує файл за стелю, сплануйте розбиття в межах того ж
PR — механічний патерн див. у розбиттях WS-AN AN3-C / AN4-F / AN4-G в
[`docs/REGISTERED_DEBT.md`](../../REGISTERED_DEBT.md).

`CHANGELOG.md` та інший документаційний/історичний контент звільнено від
цієї стелі.

## Вимоги до Pull Request

- Вкажіть ідентифікатор(и) робочого потоку, що просувається; позначте
  вихідний аудит / підзадачу в тілі коміту, а **не** в іменах
  ідентифікаторів.
- Обмежте обсяг одним зв'язним зрізом.
- Переходи мають бути детермінованими (явний успіх/помилка).
- Оновлення інваріантів/теорем супроводжують зміни реалізації.
- Синхронізуйте документацію в тому ж PR — README, SPEC, GitBook,
  CHANGELOG та `docs/codebase_map.json`, якщо змінилися джерела Lean.
- Не перейменовуйте й не видаляйте шляхи, на які посилається сайт, без
  оновлення `scripts/website_link_manifest.txt` (перевіряється на Рівні 0).
- Нуль `sorry` / `axiom` / `native_decide`, внесених у `SeLe4n/` чи
  `Main.lean`.
- Повний чек-лист див. у [`docs/DEVELOPMENT.md`](../../DEVELOPMENT.md).

## Примітка щодо безпеки CI (DOC-M08)

Робочі процеси CI в `.github/workflows/` використовують виключно тригер
`pull_request` (не `pull_request_target`). Це навмисно: `pull_request`
запускає робочий процес відносно HEAD-коміту PR без доступу до секретів
репозиторію, тому шкідливий PR не може викрасти токени. Робочі процеси, що
потребують прав на запис (наприклад, тегування релізів), живуть в окремих
файлах з обмеженим доступом, які запускаються лише на `push` у захищену
гілку та проходять ручне рев'ю.

Якщо ви додаєте новий робочий процес, за замовчуванням використовуйте
`pull_request`. Перехід на `pull_request_target` потребує рев'ю безпеки,
задокументованого в описі PR.
